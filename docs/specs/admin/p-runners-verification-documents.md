## Purpose
Let an admin open a runner's ID or selfie image for review through the logged, short-lived signed link (rows 125, 154), and show clearly when an image has been deleted at the end of its retention period (rows 144, 161), with only the minimum audit record left.

## Rules this screen follows
- Images are reached only through `GET /runners/verifications/:id/document` (admin only), which logs every call (admin, IP, time) and returns a signed URL valid at most 5 minutes. No raw storage key, path or bucket URL is ever shown or built by the client.
- **Viewing never restarts the retention clock** (row 161). The UI must not imply that opening an image keeps it longer.
- The retention clock restarts only on a new/replacement ID or selfie, a verification or re-verification started, or an admin verification review that needs the evidence (row 161). That review is either the approve/reject decision on a pending verification (the initial review) or, on an already-decided verification, the explicit, audited **Re-review evidence** action below (row 171). This screen never shows a retention date or a countdown (the clock is computed server-side and may restart).
- After the purge, only minimum audit metadata is kept (row 161): status, outcome, timestamps, reviewer/admin id, purge time, evidence type, audit/event ids. The image is gone for good; there is no restore. The reviewer's note is deleted with it (row 170).
- Never purged (row 175, kept as built): a PENDING verification's evidence, and evidence tied to an open dispute. These guards win over the retention purge; the screen shows such images as Stored. Row 190 (decided 2026-10-16): the open-dispute hold is intended, a legal/audit hold; images may stay past the retention period while the dispute is open; normal rules resume when it closes. No UI change.
- Row 191 (decided 2026-10-16): only verification activity that creates or replaces stored ID/selfie evidence restarts the clock (payment identity only if it reuses the retained images); only reviews of the stored ID/selfie count as evidence reviews; views and unrelated admin actions never do. Built on `main` (`RETENTION_CLOCK_SQL`). No UI change.
- Rows 192, 193 (decided): Cloudinary's internal disaster-recovery copies are an external dependency (System Design §10); the owner's console checklist is a production-readiness owner action. No UI change; no copy may claim deletion beyond what Nitume controls.

### Paging, loading, empty, error (whole panel)
- **Paging by runner**: a page holds whole runners; one runner's checks are never split across pages (`GET /runners/verifications/queue`, `limit` and `nextCursor` count runners). `Load more` (A-12) appends the next runners. Built safeguard: a runner that comes back on a later page (its sort key moved between pages) is merged into its card, never a second card.
- Order (built by the API per filter; confirmed by the owner 2026-10-21, BOARD row 264): `Pending` oldest pending record first (first in, first reviewed); `Rejected` and `Approved` most recently decided first; `All statuses` most recent submission first. Replaces the earlier proposal "newest `appliedAt` first". The client keeps the API order and appends pages.
- A failed `Load more` shows the same A-11 danger `Couldn't load verifications. Try again.` (accepted 2026-10-21).
- First load: `Loading…` (A-10 `.ops-loading`, as built); never the empty state before the first answer.
- Empty (load succeeded, no runner): `No applications match` + `Clear the filter, or wait for runner submissions.` (proposed: `applications` replaces `verifications` to match the per-runner cards).
- **Load error**: A-11 danger `Couldn't load verifications. Try again.` (as built). On **any** failed load (first load, refresh or filter change) the grid is **cleared** (no cards from the previous filter stay on screen under the new filter) and the cursor reset, and **the empty state is not shown** while the load error is shown (M4 notes from the re-audit). A failed `Load more` keeps the cards already shown and shows the notice with `Load more` still available. The load-error notice belongs to that failed load: the next load (Refresh, filter change, reload after a 404 / 409) removes it when it starts, so neither the cards nor the empty state of a later successful load ever sit under `Couldn't load verifications. Try again.` (clarified 2026-10-21, M4).

## Layout: document row in each verification card
Under each ID-side or selfie row of the runner card (detail line 2 in `Check rows` above), after `Submitted`:

|---|---|---|---|
| Stored | `hasDocument: true`, `purgedAt: null` | A-07 `.btn .btn-text .btn-sm` `View image` (sized to the 12 px detail row) | none |

`View image` behaviour: on click call the document endpoint, then open `url` in a new tab. Built (reviewer M1, accepted 2026-10-21): a blank tab is opened synchronously on the click (`window.open('', '_blank')`, so Safari's popup blocker does not stop the later open), detached at once (`tab.opener = null`), then pointed at the link with `tab.location.replace(url)`; it is closed when the answer has no `url` or fails. If the blank tab was blocked: `window.open(url, '_blank', 'noopener,noreferrer')`. The signed URL is never in a `Referer` (the image tab has nothing to send); the storage host receives the admin **origin** only, under the browser default `strict-origin-when-cross-origin` (no `referrer` override in the admin). Never prefetch the link (each call is logged as a view), never put it in an `href` before the click, never keep it after `expiresAt`; a second click asks for a new link.

Panel hint (A-03 sub or `.kpi-note`, once per panel, proposed): `Opening an image is logged. Images are deleted at the end of the retention period.`

## Purged verification (what an admin sees)
A purged check (its row in the runner card) keeps: the row label (below), the status (`Verified`, `Rejected`, unchanged), `Submitted` (`createdAt`), the `Reviews` rows (`Decided · {outcome} · {admin} · {time}` from `reviewedAt` / `reviewer`, re-reviews) without notes, and `Image` → `Deleted {date}`. **No `Admin note` line**: the reviewer's note is deleted at purge (row 170, decided). No `View image`, no `Re-review evidence`, no actions. The card header (name, short id, phone, area, level) is runner data and is unaffected. Checks and cards are never hidden because they were purged; the status filter works as for any runner.

Type labels (mockup rows): `government_id` → `National ID · Front` / `National ID · Back` from `side` (`front | back`, lowercase on the wire; UI shows `Front` / `Back`; rows 195, 200, decided; built on `main`, the admin view spreads `side`); a legacy ID image with `side = null` (uploaded before row 195) reads `National ID`, `selfie` → `Selfie / liveness check`, `phone` → `Phone number`, `payment_identity` → `M-Pesa identity match`.
