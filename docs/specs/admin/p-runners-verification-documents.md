## Purpose
Let an admin open a runner's ID or selfie image for review through the logged, short-lived signed link (rows 125, 154), and show clearly when an image has been deleted at the end of its retention period (rows 144, 161), with only the minimum audit record left.

## Rules this screen follows
- Images are reached only through `GET /runners/verifications/:id/document` (admin only), which logs every call (admin, IP, time) and returns a signed URL valid at most 5 minutes. No raw storage key, path or bucket URL is ever shown or built by the client.
- **Viewing never restarts the retention clock** (row 161). The UI must not imply that opening an image keeps it longer.
- The retention clock restarts only on a new/replacement ID or selfie, a verification or re-verification started, or an admin verification review that needs the evidence (row 161). That review is either the approve/reject decision on a pending verification (the initial review) or, on an already-decided verification, the explicit, audited **Re-review evidence** action below (row 171). This screen never shows a retention date or a countdown (the clock is computed server-side and may restart).
- After the purge, only minimum audit metadata is kept (row 161): status, outcome, timestamps, reviewer/admin id, purge time, evidence type, audit/event ids. The image is gone for good; there is no restore. The reviewer's note is deleted with it (row 170).
- Never purged (row 175, kept as built): a PENDING verification's evidence, and evidence tied to an open dispute. These guards win over the retention purge; the screen shows such images as Stored. Row 190 (decided 2026-10-16): the open-dispute hold is intended, a legal/audit hold; images may stay past the retention period while the dispute is open; normal rules resume when it closes. No UI change.
- Row 191 (decided 2026-10-16): only verification activity that creates or replaces stored ID/selfie evidence restarts the clock (payment identity only if it reuses the retained images); only reviews of the stored ID/selfie count as evidence reviews; views and unrelated admin actions never do. Built on `main` (`RETENTION_CLOCK_SQL`). No UI change.
- Rows 192, 193 (decided): Cloudinary's internal disaster-recovery copies are an external dependency (System Design §10); the owner's console checklist is a production-readiness owner action. No UI change; no copy may claim deletion beyond what Nitume controls.

### Approve
- One click, no dialog (mockup). While the call runs: both buttons **of that row** disabled, the clicked one reads `Approving…`; other rows stay usable. One call per click, no auto-retry.
- Call: `PATCH /runners/{runnerProfileId}/verifications/{verificationId}` `{ decision: 'approved' }`.
- Success: A-11 success `Check approved.` (proposed). No level wording in the notice; the level line updates from the answer or the next reload (Data).

### Reject (row 262, AQ-37 decided: optional internal note)
`Reject` opens an A-08 confirm dialog (it was a direct call before row 262):
- Title `Reject {check label}?` (e.g. `Reject National ID · Back?`, proposed).
- Body 13 slate-600 (proposed): `{runner} will see that this check wasn't approved and can submit it again. Your note stays internal and is never shown to the runner.` (`{runner}` = short name, else short id.)
- A-06 textarea `Note (optional)`, `maxlength` 500, counter `{n}/500` (Fira Code, counts the trimmed length), hint 11.5 slate-600 `Internal. Never shown to the runner.` (proposed). No minimum. The note is trimmed before sending; blank or whitespace-only → no `reviewerNote` sent (stored as no note). Over 500 cannot be typed.
- Buttons outline `Back`, primary `Reject check` (A-08 convention: the confirm is the dialog's primary action). Busy: `Rejecting…`, both buttons disabled, the dialog cannot close until the call settles; one call per click, no auto-retry. Initial focus on `Back`; ESC = Back.
- Call: `PATCH /runners/{runnerProfileId}/verifications/{verificationId}` `{ decision: 'rejected', reviewerNote?: string }`.
- Success: dialog closes, A-11 success `Check rejected.` (proposed); the row shows `Rejected` and, under `Reviews`, the `Admin note … · internal` line when a note was sent.
- Errors in the dialog (A-11 inside the dialog, dialog stays open with the note kept): 400 on the note length (code and extras to confirm against the api-contract HANDOFF for A-7; today the DTO allows 1000, so the client cap at 500 is what holds) → `Notes can be up to 500 characters.` (proposed); other → `Couldn't save the review. Try again.` 403, 404, 409 close the dialog and follow the Errors list below.
- The runner never sees the note or the reviewer: runner screens show only the generic rejected copy (`docs/specs/runner/v-onboard-id.md`, `v-onboard-pending.md`). API need A-8 (Data): runner-facing responses must not carry `reviewerNote`.

### Answers and errors (both actions)
- Two response shapes must work: on `main` the bare verification (no `runnerProfile`, `user`, `reviewer`, `reReviews`); with api-contract's `fix/api-verification-review` (A-3) the full list item (with `reviewer { id, displayName }`). Merge the answer over the check (`status`, `reviewedBy`, `reviewedAt`, `reviewerNote`, and `runnerProfile` / `user` / `reviewer` / `reReviews` when present), never replace it with a bare response; if the answer carries the runner's new `verificationLevel` (A-5, to confirm), update the card's level line. With the bare response `By` falls back to the admin's short id until the next reload (accepted 2026-10-21).
- After a decision the card stays in place even if the runner no longer matches the filter (e.g. last pending check decided under `Pending`); it leaves on the next load or refresh (proposed: no card jumping under the admin's cursor). The topbar count updates at once (minus one when the runner has no pending check left).
- 403 → `FORBIDDEN_COPY`; 409 `verification_already_decided` `{ status }` (another admin decided first, A-2) and 404 (unknown verification or not this runner's; on `main` also the already-decided case) → reload and A-11 info `This check was already decided. The list is updated.` (proposed); 400 (malformed id) and other → `Couldn't save the review. Try again.`

### Paging, loading, empty, error (whole panel)
- **Paging by runner**: a page holds whole runners; one runner's checks are never split across pages (A-5 runner-grouped list). `Load more` (A-12) appends the next runners. Fallback while only per-check items exist: group the loaded items by `runnerProfileId`; when `Load more` brings more checks of a runner already on screen, merge them into that card (never a second card for the same runner).
- Order: newest `appliedAt` first (as the current list, newest first; proposed).
- First load: `Loading…` (A-10 `.ops-loading`, as built); never the empty state before the first answer.
- Empty (load succeeded, no runner): `No applications match` + `Clear the filter, or wait for runner submissions.` (proposed: `applications` replaces `verifications` to match the per-runner cards).
- **Load error**: A-11 danger `Couldn't load verifications. Try again.` (as built). On **any** failed load (first load, refresh or filter change) the grid is **cleared** (no cards from the previous filter stay on screen under the new filter) and the cursor reset, and **the empty state is not shown** while the load error is shown (M4 notes from the re-audit). A failed `Load more` keeps the cards already shown and shows the notice with `Load more` still available.

Never prefetch the link (each call is logged as a view), never put it in an `href` before the click, never keep it after `expiresAt`; a second click asks for a new link.

Panel hint (A-03 sub or `.kpi-note`, once per panel, proposed): `Opening an image is logged. Images are deleted at the end of the retention period.`

## Re-review evidence (row 171, decided 2026-10-16)
Owner: "the decision on a pending verification is the initial review; a later review of stored evidence needs an explicit, audited 'Re-review evidence' action (admin, timestamp, verification/evidence reference, review event). Viewing never restarts the clock."

When shown: verification status `approved` or `rejected`, type `government_id` or `selfie`, `hasDocument: true`, `purgedAt: null`. Never on a pending verification (its decision is the initial review; use `Approve` / `Reject`), on a purged or missing image, or on `phone` / `payment_identity` checks.

1. Button: A-07 `.btn .btn-outline` small `Re-review evidence`, in that check's actions line (detail line 5; decided checks have no `Approve` / `Reject`). Not green: it is not the primary action of the panel and it changes no decision. 40 px target.
2. Confirm (A-08 dialog):
   - Title `Re-review this evidence?`
   - Body 13 slate-600: `This records that you are reviewing the stored {type label} for {runner} again. The review is logged with your name and the time, and the image is kept for a new retention period from today. Opening the image alone never does this.`
   - Optional A-06 textarea `Note (optional)`, max 500, counter `{n}/500` (Fira Code), hint 11.5 slate-600 `Kept in the audit trail until the image is deleted.` Optional, no minimum (row 180); whitespace-only is sent as empty and stored as no note.
   - Buttons outline `Back`, primary `Record re-review` (disabled and `Recording…` while the call runs; one call per click, no auto-retry).
3. On success: A-11 success `Re-review recorded.`; the check's `Reviews` list gains the new row; `View image` stays where it is (opening the image is a separate, logged step, as always). The client never shows a new retention date (rule above).
4. Activity (`.drawer-row` list under the check, detail line 3 of `Check rows`, label `Reviews`, oldest first; each time 12-hour EAT, Fira Code):
   - `Decided · {Approved | Rejected} · {admin} · {reviewedAt}` (from the verification).
   - one row per re-review: `Re-reviewed · {admin} · {createdAt}`, with the note on a second line 12 slate-600 when present.
   - On a purged card the rows stay (they are audit/event metadata, row 161) but the notes are gone (row 170).

Errors:
- 409 `verification_not_decided` → reload, A-11 info `Decide this check first.`
- 410 `verification_document_purged` (extra `purgedAt`) → card to Deleted, A-11 info `This image was deleted at the end of the retention period, so there's nothing to re-review.`
- 404 `verification_document_missing` → `No image on file`, A-11 info `No image is stored for this check.`
- 403 → `FORBIDDEN_COPY`; other → `Couldn't record the re-review. Try again.`

## Purged verification (what an admin sees)
A purged check (its row in the runner card) keeps: the row label (below), the status (`Verified`, `Rejected`, unchanged), `Submitted` (`createdAt`), the `Reviews` rows (`Decided · {outcome} · {admin} · {time}` from `reviewedAt` / `reviewer`, re-reviews) without notes, and `Image` → `Deleted {date}`. **No `Admin note` line**: the reviewer's note is deleted at purge (row 170, decided). No `View image`, no `Re-review evidence`, no actions. The card header (name, short id, phone, area, level) is runner data and is unaffected. Checks and cards are never hidden because they were purged; the status filter works as for any runner.

Type labels (mockup rows): `government_id` → `National ID · Front` / `National ID · Back` from `side` (`front | back`, lowercase on the wire; UI shows `Front` / `Back`; rows 195, 200, decided; built on `main`, the admin view spreads `side`); a legacy ID image with `side = null` (uploaded before row 195) reads `National ID`, `selfie` → `Selfie / liveness check`, `phone` → `Phone number`, `payment_identity` → `M-Pesa identity match`.

## Errors on `View image`
- 410 `verification_document_purged` (extra `purgedAt`): switch the row to Deleted with that date; A-11 info `This image was deleted at the end of the retention period.`
- 404 `verification_document_missing`: row to `No image on file`; A-11 info `No image is stored for this check.`
- 200 with `url: null` (console storage driver in dev): A-11 info `Image preview isn't available in this environment.`
- 403 → `FORBIDDEN_COPY`; other → `Couldn't open the image. Try again.`
